# Final Completion Pass — FC-11: Performance + index review

**Scope:** the query surfaces added/expanded earlier in this Final Completion Pass (commit `accf7bf`, diffed against `16d81e6`) plus two work-streams landing concurrently in the same working tree while this review ran (visible as uncommitted changes at review time — `data-quality.service.ts`'s `checkDuplicate()` and `creator360.service.ts`'s `submissions()`/`timeline()` additions). **Method:** read every changed query against the current `packages/database/prisma/schema.prisma`, then verified against a live Postgres 16 instance (`localhost:5432/influenceos`, migrated to this branch's HEAD — 662 Influencers, 16,701 ActivityLog rows, 94 BrandInfluencer, 92 CampaignInfluencer, 36 ProductShipment, 51 Deliverable, 10 DeliverableSubmission, 0 UsageRight) using `EXPLAIN (ANALYZE, BUFFERS)` on the *exact* SQL Prisma compiles (captured via query-event logging, not guessed). Every "genuine gap" claim below has a real before/after `EXPLAIN` behind it.

The two plain B-tree ones (`ActivityLog.publishedContentId`, `Influencer.mobile`/`whatsapp`) are also declared in `schema.prisma` as ordinary `@@index([...])` entries, generated and verified with `prisma migrate diff` against a shadow database replaying this branch's full migration history. The trigram GIN and the expression index are **not** representable in Prisma's schema DSL at all (no operator-class support for third-party extension opclasses like `gin_trgm_ops`, and no functional/expression index support full stop) — they're hand-written raw SQL in the same migration file, following the exact precedent already established by `20260919003341_wave7_directory_indexes_cursor` (W7-2's trigram indexes), including the `CREATE EXTENSION IF NOT EXISTS pg_trgm;` / `IF NOT EXISTS` idempotency style.

## Migration status

**Applied to a live DB**, not hand-written-and-unverified. `prisma migrate dev` refused to run ("environment is non-interactive"), so the workflow was: edit `schema.prisma` → `prisma migrate diff --from-migrations ... --to-schema-datamodel ... --script` (against a throwaway shadow DB replaying this branch's real migration history) to get engine-verified `CREATE INDEX` DDL for the two schema-representable indexes → hand-assembled `migration.sql` combining that DDL with the two raw-SQL indexes above (styled like the W7-2 precedent) → applied with `prisma migrate deploy` (the non-interactive-safe path the CLI itself points to) against the same dev Postgres the rest of this session was using → confirmed with `prisma migrate status` ("Database schema is up to date!") and `\di+` showing all five indexes live → re-ran `EXPLAIN (ANALYZE, BUFFERS)` on the exact Prisma-compiled queries against the now-migrated live DB to confirm the plan actually changed (not just that the index exists). `npx prisma generate` was re-run afterward so the Prisma Client types reflect the new indexes (indexes don't change generated types, but this keeps the client in sync with schema.prisma as a matter of course).

One caveat: `prisma migrate diff --to-schema-datamodel` also proposed *dropping* the five existing W7-2 raw-SQL trigram indexes, because nothing in `schema.prisma` represents them (this is inherent to diffing a live/replayed DB against a pure-schema target, not specific to this session's changes) — those `DROP INDEX` statements were discarded and never applied; only the two genuine `CREATE INDEX` statements for the new plain-column indexes were kept.

## Deliberately NOT indexing the `meta.shipmentId` path a different way (GIN on `meta`)

The task flagged this specific filter as one to justify explicitly either way. A GIN index on the whole `meta` JSONB column (the "obvious" JSONB-indexing move) was considered and **rejected** in favor of the narrower expression index actually added above, because:
- Prisma compiles `path: ['shipmentId'], equals: X` to an equality comparison on the **extracted** value (`meta #> ARRAY['shipmentId']::text[] = '"X"'::jsonb`), not a containment check. Postgres's `jsonb_ops`/`jsonb_path_ops` GIN operator classes only accelerate `@>`/`?`/`?|`/`?&` — **not** `#>` path-extraction equality. A GIN index on `meta` would sit there unused by this exact query (confirmed: it's the `#>`/extraction form, not `@>`, in the captured SQL).
- Even if the query were rewritten to use `@>` (it isn't, and changing that is a service-layer decision outside this review's file scope), a GIN index indexes every key/value pair in every row's `meta` blob — `meta` also carries `status`, `deliverableId`, `event`, `assignedToUserId`, etc. for shipment-adjacent activity, plus entirely unrelated shapes for every other `ActivityType`. That's a much heavier index to write-maintain than a targeted expression index on one path, for no additional read benefit on this specific query.
- The targeted expression index that *was* added matches the compiled query exactly and was measured (see the table above) to turn this into an Index Scan.

## Query-shape recommendations (no schema change needed)

- **`activity.service.ts`'s `shipmentId` filter**: no change needed now that the expression index exists, but if this filter is ever reshaped to use `contains`/`array_contains` instead of `path`+`equals`, re-verify the compiled SQL still matches the indexed expression — Prisma's JSON filter compilation is sensitive to exactly which filter shape is used (`equals` vs `array_contains` vs `string_contains` compile to different SQL operators).
- **`data-quality.service.ts::checkDuplicate()`**: the `displayName: { contains, mode: 'insensitive' }` branch already benefits from the existing `Influencer_displayName_trgm_idx` (W7-2) — no change needed, just noting it was checked, not overlooked.
- **`shipment.service.ts::listForDeliverable`**: already fully covered by the existing `ProductShipment.deliverableId` index — no schema change needed. (See the flagged scope-check gap below, which is a correctness issue on this same function, not a performance one.)
- **`submission.service.ts`**: every scope-check query (`deliverable.findUnique`, `deliverableSubmission.findUnique`, `campaign.findUnique`, all by `id`) resolves through the primary-key index — nothing to add. The one `findMany` (`listForCampaign`, filtered by `deliverable: { campaignInfluencer: { campaignId } }`) walks an already-fully-indexed FK chain (`Deliverable.campaignInfluencerId` → `CampaignInfluencer.campaignId`), same reasoning as the Creator-360 row above.

## Flagged for follow-up (not fixed here — outside this review's file scope)

These are correctness issues found while reading, not performance ones, so they were **not** fixed (fixing service logic is outside this task's allowed files: only `schema.prisma`/migrations/this doc). Flagging per the task's instructions:

1. **Missing brand/country scope enforcement on `GET /deliverables/:id/shipments`.** `shipment.service.ts::listForDeliverable(deliverableId)` runs `prisma.productShipment.findMany({ where: { deliverableId } })` with no brand-scope or country-scope check at all, unlike every sibling function on the same service (`loadDTO`, `listForCampaignInfluencer` via `ciContext`, `update`, `updateStatus`, `assign` — all call `isBrandOutOfScope`/`isCountryOutOfScope` against `scopedBrandIds`/`scopedCountryCodes`). The route (`apps/api/src/routes/shipments.routes.ts`) only requires `requireAuth`, no additional scope check either. A brand- or country-scoped actor (e.g. a KW-only Logistics operator, or a user with `UserBrandAccess` rows limiting them to one brand) can reach shipment details — including the address/phone fields, unless separately redacted by the `LOGISTICS_ADDRESS_VIEW` capability check that *is* still applied — for any deliverable outside their scope simply by knowing or guessing its id. This is the same "direct-ID authorization" class of bug the rest of this service's doc comments explicitly call out as something they guard against everywhere else.
2. **`data-quality.service.ts::report()`'s `campaign-no-owner` deep link is inert.** The finding links to `/campaigns?ownerMissing=1`, but (per the existing code comment on that line) `campaign.service.ts`'s `buildWhere()` doesn't implement an `ownerMissing` filter param — clicking the finding won't actually filter anything. This is called out in the source as a known pre-existing gap already, not new, but repeating it here since it's adjacent to what this review touched.
